# Nikki 在用线路提醒

## 工作方式

50.2 上的 `cfsm-nikki-watch` 每 60 秒只读本机 Mihomo `/connections`、`/proxies`、`/rules`、`/configs`，读取实际连接、分流选择和当前运行 provider。只上传 Monitor 节点 ID、确定的 IPv4/IPv6 地址族、入口活跃连接数、出口活跃连接数、是否被分流选中与时间；不上传访问域名、客户端 IP、代理密码或策略组名称。

## 入口颜色

- 绿色：最近 5 分钟内观察到连接字节实际增长的公网入口。
- 黄色：分流规则当前选中的入口，但尚未检测到近期流量。只解析规则实际引用的策略组，并递归跟随其当前选择，不把未选择的候选节点或无规则引用的闲置策略组计入。全局模式只跟随 `GLOBAL`；直连模式没有待用代理入口。
- 蓝色：近 5 分钟有流量增长的中转路线海外出口；同时作为活跃入口时绿色优先，入口低分时仍红色优先。仅出口角色不触发入口低分提醒。
- 灰色：其他节点或当前没有可确认的关联。无法确定地址族和超过 150 秒的陈旧采集结果不会继续标绿/黄，因此灰色不保证节点未被其他客户端使用。
- 红色优先：有实时流量的入口低于 60 分时仍显示告警色。仅待用的入口不触发连续低分告警。

`Nikki → HK → HKS` 标记 HK 为入口、HKS 为出口；直接连接 HKS 则 HKS 为入口。客户端 `dialer-proxy` 递归解析首跳，最终代理端点作为出口。服务器内部中转由采集器私有配置 `relay_exits` 精确匹配入口域名/IP、端口和地址族，不根据节点名称猜测。VPS 评分不代表海外中转后整条线路。`DIRECT` 不关联；域名入口只有明确强制 `ipv4` / `ipv6` 时才关联，`ipv6-prefer` 等可回退设置不会被猜测。

启动后的第一轮不把历史累计字节当作实时活动，先显示已选择入口的黄色状态；下一轮检测到字节增长后变绿。切换策略时仍有流量的旧连接继续标绿，新选中但空闲的入口标黄。同一节点同一地址族同时满足两者时，绿色优先。

Worker 与主题同步采用当前估算 v0.6。现有移动双栈 `node_1` / `node_2` 探针只取近 10 分钟，延迟计分使用 70% 当前延迟＋30% 近期 P95，不足 3 个采样时用当前延迟；失败率按近期有效样本权重平均，波动按近期相邻有效采样计算。带宽只采用时间最近一批双向常规测速，下载 / 上传占 70% / 30%。历史晚高峰只作参考，不混入当前分数。超过 1 小时标明带宽非当前实测，超过 6 小时标为较早参考，72 小时失效；不因此更改节点既有定时或自动补测策略。页面的在用线路直接显示后台本次评分及依据，保持显示与提醒一致；未使用线路维持原来的前端评分。公式位于 `src/utils/networkEstimate.js`，由 SAO 的 `src/utils/networkEstimate.ts` 导出，修改公式时两端须同步。移动探针对应字段改变时须调整 `scoreProbe`，不能套用其他运营商。

## 刷新与一致性

前端每 15 秒请求线路状态；同标签页刷新先复用按站点及登录身份隔离的 `sessionStorage` 快照，仍以原采集时间计算 150 秒有效期，重复读取不会续期。偶发请求失败保留尚有效的状态并在悬浮提示说明；成功的空快照立即清除旧标记，过期快照不会继续标绿/黄。缓存不保存完整登录凭据。

后台评分期间保留上一份完整快照，路线、清理与版本在同一 D1 事务发布，状态查询也使用单个事务读取，避免半更新或读写交错导致颜色闪失。并发迟到及相同时间的重放报告不覆盖已发布结果。

入口映射按实际 `server` 域名或 IP 精确匹配，不能从代理名称推断。2026-10-17 补齐已验证的 `lax.bjhaha.cc`；后续更改入口域名时应同步 `/etc/cfsm-nikki-watch/config.json` 的 `endpoints`。日志 `unknown` 非零表示仍存在未识别入口。

本次回滚基线：Worker / SAO 本地 `backup/pre-route-cache-20261017`；路由器配置 `/root/cfsm-nikki-backups/20261017-route-cache/config.json`。

## 提醒规则

- 在用线路低于 60 分连续 5 分钟后，复用 Monitor 已配置的通知渠道提醒一次。
- 恢复到 65 分后解除；60–64 分保留已触发事件，避免反复提醒。
- 没有有效评分时显示数据不足，打断低分计时，不补零。
- 采集间隔超过 150 秒时清除在用标识并重新计时，避免用陈旧线路发提醒。
- 没有通知渠道或发送失败时，评分依据弹窗显示原因，后续上报继续重试。
- 只提醒，不写 Mihomo API，不切换节点，不改路由、Nikki profile、代理或防火墙。

## 运行与回滚

路由器命令：

```sh
/etc/init.d/cfsm-nikki-watch status
logread -e python3 | grep '"phase"'
/usr/bin/python3 /usr/libexec/cfsm-nikki-watch.py --once --dry-run
```

只停止联动：

```sh
/etc/init.d/cfsm-nikki-watch stop
/etc/init.d/cfsm-nikki-watch disable
```

150 秒后页面在用标识自动失效。原有探针和测速继续运行。回滚基线为 Worker / SAO 的本地 `backup/pre-nikki-link-20261017` 分支；线上主题旧版本为 `1ea8176cc4106e7bcd988c0814ce35886e9506fd`。

绿/黄/灰三态改造前另有 Worker / SAO 本地 `backup/pre-nikki-route-states-20261017` 分支，路由器采集器及配置备份在 `/root/cfsm-nikki-backups/20261017-route-states/`。回滚三态改造时应同步恢复后台、主题和采集器；修改的只是独立监测服务，Nikki 原配置保持不动。

配置 `/etc/cfsm-nikki-watch/config.json` 权限 600。其上报凭证由 deb 的独立 runner 密钥通过 HMAC 派生，仅能调用 `/api/nikki/report`，不能调用测速或管理接口。不要输出、提交或公开该配置。采集器不进行 iperf 测速，增加的流量只有每分钟小型 HTTPS 上报。

## 重传辅助项（v0.4）

保留延迟 30%、失败率 20%、带宽 40%、波动 10% 主分，再减去最多 3 分的重传辅助惩罚。每方向用 `retransmits / (mbps × 1000000 × duration_seconds / 8 / 1048576)` 估算每 MiB 重传次数，按下载 70%、上传 30% 合并。此分母为吞吐乘配置时长的近似传输量，不是抓包统计，所得指标不是丢包率。

自定义曲线：每 MiB 重传 0 / 1 / 10 / 100 / 500 次对应单方向扣分 0 / 0.1 / 0.5 / 2 / 3；中间按 `log1p` 插值，超过上限不继续增加。没有行业标准含义，后续依据实测体验校准。

只用与带宽同一批测试，缺少计数或时长、失败、估算传输量小于 1 MiB 时该方向不计，不伪装成零重传，也不因另一个方向缺项放大已有惩罚。零重传只表示该方向本次没有记录到 TCP 重传，不代表另一方向、其他路径或其他时间也无损。

在原有评分依据弹窗中展示估算强度、缺项与实际扣分，不新增首页行。不修改测速频率、采集器、数据库结构或原始历史。回滚基线为 Worker / SAO 本地 `backup/pre-retrans-score-20261017`，旧主题版本 `16b176b7b1c2b238ff8a8cf34c42a4701844ec07`。

## 中转出口识别与回滚

采集协议 v3 新增 `exit_connections`，D1 幂等增加同名列，状态接口仅输出 `exit_active` 布尔值；v1 / v2 仍兼容并将出口计数视为 0。入口 `connections` 与出口计数分别合并，出口身份不覆盖入口身份。

2026-10-17 只读验证 HK 的 Realm：`[2400:c620:26:2b::a]:18450 → hks.bjhaha.cc:18445`，`18449 → hkg.bjhaha.cc:443`，两份配置均 `network.ipv6_only=true`，前者还核对到当前 IPv6 连接。私有 `relay_exits` 记录对应 HK 域名/IP 别名及 HKS/HKG 的 IPv6 节点 ID。未来改服务器内部转发配置时，需同步映射；无法核实的海外出口不会推测着色。

仅扩展原徽章颜色与依据说明，不修改线路评分、Nikki profile、选线、Realm 或路由配置。前后端本地回滚分支 `backup/pre-relay-blue-20261017`，旧主题版本 `a1ffc7d87d485cf5fd17e950f8b22eb62c328e56`，路由器原采集器及私有配置保存在 `/root/cfsm-nikki-backups/20261017-relay-blue/`。回滚时先恢复采集器旧协议，新增列可保留。

## 带宽标尺校准（v0.5）

按用户反馈，原曲线 100 Mbps 即带宽单项 65 分，导致约 127 Mbps、其他指标良好时总分接近 80，不能体现其与 500 Mbps 线路的体验差距。统一改为 1 / 10 / 50 / 100 / 200 / 300 / 500 / 1000 / 2000 Mbps 对应 5 / 15 / 30 / 40 / 55 / 65 / 80 / 95 / 100 单项分，区间按 log1p 插值。下载 / 上传 70% / 30% 与总带宽权重 40% 均保持原值，重传仍最多扣 3 分。该曲线是个人体验校准，不是官方 AIM 标准，也不保证达到某速度必然得到某总分。

按 2026-10-17 18:31 核查的 HKG V6 同一组输入（126.7 / 130.2 Mbps；其余单项延迟 81、失败率 100、波动 95.4、重传扣 1.61）重算，总分从约 80 降至约 70。实时分数仍随新采样变化。回滚分支：Worker / SAO `backup/pre-bandwidth-calibration-20261017`；旧主题固定版本 `0545815f40f1b9284a5564d906414f292431fef2`。

### 用户进一步校准（v0.6）

用户明确指定 100 Mbps 带宽单项 20 分，200 Mbps 以下实际使用有卡顿感。最终锚点改为 1 / 10 / 50 / 100 / 200 / 300 / 500 / 1000 / 2000 Mbps 对应 1 / 5 / 10 / 20 / 40 / 60 / 80 / 95 / 100 分；维持连续 log1p 插值及原有总权重，不设 200 Mbps 硬跳变。v0.5 的较宽松锚点已被本规则取代。此处为带宽单项分，不是总分。

### 连续评分与显示精度（v0.7）

带宽锚点之间原本已连续按 log1p 插值，并非 500–1000 Mbps 共用一档。保持 v0.6 标尺及权重，在原有评分依据中增加 500 / 600 / 700 / 800 / 900 / 1000 Mbps 的动态换算对照；总分统一保留一位小数，避免整数舍入掩盖差异。前后端均使用模型版本 7，数据库和状态接口保留小数；旧缓存的模型不用于新徽章评分。该精度用于比较，不代表测量误差只有 0.1 分。

用户随后要求总分不显示小数：页面徽章及依据标题恢复整数显示；内部小数与连续换算保留，避免在计算环节提前取整。
